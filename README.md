# NP3 → NCP：把尼康云创滤镜装进老机身

一个纯静态网页工具，把尼康云创（Nikon Imaging Cloud）下载的 **.NP3 / .NP2** 滤镜，
转成 D300 / D300S / D90 等老机身能读的**自定义优化校准 .NCP**。

**在线使用**：<https://pinksert.github.io/np3-to-ncp/>

打开网页 → 拖入 .NP3 → 得到 .NCP → 拷进存储卡的 `NIKON\CUSTOMPC`。
全程在浏览器里计算，滤镜文件和照片都不会上传到任何服务器。

---

## 它解决的是什么问题

尼康云创的滤镜只对新机器（以及 NX Studio）开放。老机身吃的是另一套文件格式：
自定义优化校准（.NCP），一个 638 字节的小文件，里面是一条 257 点的影调曲线
加 8 个滑块。

两种格式之间没有官方转换工具。这个项目做的事情是把两者对上：

| 项目 | NP3（云创滤镜） | NCP（老机身优化校准） |
|---|---|---|
| 文件大小 | 248–332 字节，22 张参数卡 | 52 或 638 字节，2 条记录 |
| 影调曲线 | **文件里没有** | 257 点 × 16 位 LUT |
| 滤镜身份 | 卡 3 里的 2 字节底子编号 | 底子编号 + 8 个滑块 |
| 清晰度 / 效果级别 / 快速锐化 | 有 | **没有对应字段** |

## 最关键的一点：NP3 里没有曲线

把 28 个 NP3 全部拆开看：每个文件 22 张卡片，除了名字和参数卡之外，只有卡 3
存了一个 2 字节的**底子编号**（DREAM=0801、SILENCE=0807、FLAT=028E …）。
滤镜真正的影调与色彩，在 NX Studio / 云创的软件里，由那个编号查出来，
文件本身一个字都没带。

所以「导入 NP3 就得到 NCP」只有两条路：

1. **这个底子编号已经被量过** —— 直接从标定库里取那条曲线，一步出文件；
2. **没量过** —— 用这个滤镜实际处理一张标定图，程序从结果里把曲线读出来。

没有第三条路。硬要「按编号猜」只会得到一个看起来像、其实不像的文件。

### 标定怎么做的

网页会给你一张 2048×1024 的标定图：上半是 256 级灰阶（每级 8 像素宽），
下半是 32 块色卡。你在 NX Studio 里用目标滤镜导出它，再把导出的图传回来。

因为程序知道这张图每个像素原本是多少，所以：

- 灰阶条 → 直接读出 256 个亮度点，得到 T(x)，**是测量不是拟合**；
- 色卡 → 得到整体彩度倍率与色相旋转，换算成饱和 / 色相档位；
- 成片几乎没有彩度 → 判定单色系，再按色相角对到 10 个调色档之一。

实测这套流程的自洽性：合成反解曲线差 0.00、经 JPEG q92 压缩后 ≤ 1.0 级、
写进文件再按 `C(H(x))` 读回 0.01–0.13 级。

用真实照片反解会差得多（26–42 级）—— 普通照片不可能覆盖 0 和 255，
没覆盖的区间只能靠外推。这就是必须用标定图而不是「随便传张照片」的原因。

## 机身曲线预补偿（最容易踩的坑）

机身执行的是 `C(H(x))`：先把输入亮度过一个固定的前变换 H，再交给曲线。
所以想让成片得到目标曲线 T(x)，写进文件的必须是 `C = T ∘ H⁻¹`。

漏了这一步，文件能生成、机身也认，但成片全程偏暗、暗部发死。

H 是用「恒等曲线」量出来的：套上去之后中间调暗 18 级、两端归零。

## 已知限制

- **清晰度 / 效果级别 / 快速锐化会丢失**。这三项在 NCP 格式里没有位置，
  是格式差异，不是转换出错。
- **AUTO 做不了**。它是跟着场景自动变的底子，机身里没有一个固定曲线能对上它。
- **滑块会被钳位**。NP3 的锐化可能是 −0.5，老机身的范围是 0–9；
  超出范围的会在页面上标出来。
- **底子编号才是身份，不是名字**。实测有名字叫 DREAM、底子却换成 0815 的文件，
  那是另一支滤镜。所以匹配只认编号；只有编号读不出来时才退回按名字找。
- 标定图导出时**不要改尺寸**，色彩空间用 sRGB。改了尺寸程序会直接拒绝并说明原因。

## 本地运行

纯静态，没有任何构建步骤，也没有后端：

```bash
git clone https://github.com/Pinksert/np3-to-ncp.git
cd np3-to-ncp
python -m http.server 8000
# 打开 http://127.0.0.1:8000/
```

直接双击 `index.html` 用 `file://` 打开不行 —— 浏览器会因为跨源策略拒绝
读取 `library.json`。

## 文件结构

```
index.html      页面与全部交互逻辑
np3core.js      格式解析、曲线数学、标定图反解（np3core.py 的浏览器移植）
library.json    标定库：31 个 NCP，覆盖 27 个滤镜底子（base64 内嵌）
assets/         标定图
```

## 和 Python 版的关系

同目录树下的 `np3tool/` 是本地 Python 版（带 http 服务器、能直接写存储卡目录）。
网页版是它的纯前端移植，算法逐函数对应。

两者的输出做过逐字节比对（`np3core.js` 的 `pyRound` 就是为此存在的：
Python 的 `round()` 是四舍六入五取偶，JS 的 `Math.round` 是五入向上，
在 .5 边界上会差 1 个 15 位单位，文件就对不上了）：

- 28 个 NP3 的解析结果：28/28 一致
- 31 个 NCP 的读取结果：31/31 一致
- 读回 → 重写 → 逐字节比对：30/30 一致
- 标定图反解（彩色 / 纯灰 / 单色+调色三条分支）：曲线最大差 0.000000
- 滑块组合 90 组：90/90 一致
